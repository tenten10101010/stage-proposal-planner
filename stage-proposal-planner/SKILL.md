# Stage Proposal Planner

## Purpose

Turn scattered project inputs into a coherent stage proposal that can be read, discussed, or presented. The output may be a document, report, PPT outline, slide-by-slide script, or image-led deck concept.

Do not treat the user's raw discussion as the final narrative. Extract the current-stage logic the audience needs to understand.

## Default Workflow

### 1. Define the Use Case

Identify before writing:

- Audience: internal decision-maker, external partner, supplier, channel, investor, public audience, or execution team.
- Goal: explain, persuade, secure resources, align decisions, report progress, or guide execution.
- Final artifact: document, report, PPT, visual deck, one-page brief, or execution order.
- Decision required: continue, adjust, stop, invest, cooperate, approve, recruit, or execute.

If the user does not specify the artifact, infer it from the scenario and state the assumption. Ask only when different outputs would materially change the work.

### 2. Inventory the Inputs

Ask for or inspect only what is needed:

- Source facts: company background, project origin, current stage, scope, numbers, evidence, partner status.
- Raw thinking: meeting transcript, voice notes, chat history, screenshots, rough diagrams.
- Existing assets: brand deck, past proposal, visual references, approved pages, logos, product screenshots.
- Execution facts: current workstreams, responsible parties, partner asks, resource constraints, timeline.
- Proof materials: user feedback, reports, test results, interviews, content samples, community records.

Separate:

- confirmed facts;
- user intent and strategic judgment;
- inferred structure;
- unverified claims;
- visual or narrative preferences.

Do not invent metrics, approvals, partner relationships, certifications, or outcomes.

### 3. Convert Messy Material Into a Present Logic

Do not reproduce the meeting process unless the audience needs it. Most proposals should show the current coherent project, not the path of how the team thought its way there.

Build the logic in this order:

1. Why this project exists now.
2. What larger brand/company foundation it rests on.
3. What project it is at the current stage.
4. What modules or workstreams it contains.
5. What role each module performs.
6. How modules feed each other.
7. What assets or evidence are being accumulated.
8. What value is created for each stakeholder.
9. What resources or decisions are being requested.
10. What the next stage looks like.

Use a simple causal chain:

```text
Foundation -> Project proposition -> Operating modules -> Evidence/assets -> Stakeholder value -> Resource ask -> Next action
```

### 4. Choose the Right Artifact

Use this decision:

- **Document**: use when the user needs a full explanation, policy, brief, or copy that can be edited.
- **Report**: use when evidence, analysis, status, and decisions are central.
- **PPT / visual deck**: use when the user needs to present, pitch, negotiate, or align stakeholders quickly.
- **One-page brief**: use when the user needs a compact conversation aid.
- **Execution order / brief**: use when the user needs suppliers or partners to act.

For PPTs, first produce the storyline and page plan. Do not jump into slide production before the logic is stable, unless the user explicitly asks for visual exploration.

### 5. Build the Storyline

For external proposals, prefer:

```text
1. Opening proposition
2. Company / brand credibility
3. Project origin or current need
4. Brand philosophy
5. Project definition
6. Structure or operating model
7. Core modules
8. Evidence or pilot proof
9. Value for users / brand / partners
10. Collaboration scenarios
11. Resource ask
12. Next-step invitation
```

For internal stage reports, prefer:

```text
1. Current judgment
2. What has been tested or built
3. Evidence and signal quality
4. What remains uncertain
5. Options and tradeoffs
6. Recommended decision
7. Next-stage plan
```

For partner negotiation decks, make the ask explicit:

- what the project is;
- why it is credible;
- why the partner matters;
- what the partner provides;
- what the partner receives;
- how cooperation starts safely.

### 6. Write Each Section by Function

Every section or slide needs one job. Use functional labels while drafting:

- Credibility: prove why the proposer can do this.
- Proposition: state what the project is.
- Structure: show how parts relate.
- Evidence: show what has happened or what is known.
- Human value: show why it matters beyond operations.
- Partner value: show why others should join.
- Resource ask: state what is needed.
- Next step: make the conversation actionable.

If a section only repeats earlier information, merge or delete it.

## Handling Complex Modules

When a project has many connected parts, avoid a maze. Create:

- one clean total structure page;
- one page per major module;
- one relationship page showing flows;
- optional subchapter pages for high-value modules.

For relationship diagrams, distinguish:

- resource flow;
- asset accumulation;
- collaboration relationship;
- user growth or feedback loop.

Use different line styles or colors only when they explain meaning.

## Evidence and Claims

Use strong claims only when supported. For each number or proof point, identify:

- source;
- date or stage;
- scope;
- what it proves;
- what it does not prove.

Convert pilot results into strategic proof carefully:

- Good: "More than 200 participants completed a 7-day check-in, creating feedback and observation records that can support product learning."
- Avoid: "The product has been scientifically proven effective" unless that is actually verified.

## Visual Output

When the user asks for PPT, deck pages, image previews, or visual style, read `references/visual-guidance.md`.

Before generating visuals, lock:

- page purpose;
- exact text;
- visual hierarchy;
- which facts are allowed;
- whether people, animals, products, screenshots, or abstract diagrams should appear.

For batches, keep the storyline stable and vary composition intentionally. Do not let speed collapse the deck into repetitive templates.

## Review Checklist

Before handing off:

- The proposal answers "why now" and "why us".
- The current-stage logic is shown, not just the thinking history.
- Every module has a role and contributes to other modules.
- Evidence is separated from ambition.
- Partner/resource asks are explicit.
- Visuals support the argument rather than decorating it.
- Repetitive slide patterns are broken at section changes.
- The final artifact matches the user's real use case.
